# PGM-H

A decision-support workload derived from TPC-H: the 8-table schema of
parts, suppliers, customers, orders and line items, and 22 read-only
analytical queries with random parameters. It is meant for a single client
and read by the per-query response times; the headline figure is queries per
hour.

```bash
pgmeter spec new pgm-h -o .
pgmeter -d benchmark init --spec pgm-h -s 1 -j 4
pgmeter -d benchmark run  --spec pgm-h -c 1 --once      # power test: each query once
pgmeter -d benchmark run  --spec pgm-h -c 4 --once      # throughput test: four streams
```

## Scale and data

The scale unit is the TPC-H **scale factor**. Per unit:

| Table | Rows per unit | Notes |
|---|---|---|
| `supplier` | 10,000 | |
| `part` | 200,000 | |
| `partsupp` | 800,000 | 4 suppliers per part |
| `customer` | 150,000 | |
| `orders` | 1,500,000 | spread over 1992 to 1998 |
| `lineitem` | about 6,000,000 | 1 to 7 lines per order, prices, discounts, ship, commit and receipt dates |

`region` (5 rows) and `nation` (25) are loaded once. Scale factor 1 is about
2 GB with indexes and loads in a minute or two on a fast server; scale
factor 10 is ten times that. At scale factor 1 there is a single unit, so
the load itself runs on one connection; `-j` still parallelizes the keys,
the indexes and the vacuum. Keys are `integer` and dates are `date`,
as the TPC-H data types prescribe. Besides the primary keys and eight
foreign keys, the spec creates the indexes an analytical PostgreSQL setup
usually has: `lineitem` on ship date, order key, part key, supplier key and
(part key, supplier key); `orders` on customer key and order date;
`partsupp` on supplier key; `customer` and `supplier` on nation key. They
are listed in the spec and easy to remove if your comparison needs a
narrower schema.

## The queries

The 22 queries follow the TPC-H query definitions, with their parameters
drawn at random within the ranges the specification gives (dates, regions,
brands, discounts, quantities):

| | | |
|---|---|---|
| Q1 Pricing summary | Q9 Product profit | Q16 Parts and suppliers |
| Q2 Minimum-cost supplier | Q10 Returned items | Q17 Small-quantity orders |
| Q3 Shipping priority | Q11 Important stock | Q18 Large-volume customers |
| Q4 Order priority | Q12 Shipping modes and priority | Q19 Discounted revenue |
| Q5 Local supplier volume | Q13 Customer distribution | Q20 Potential promotion |
| Q6 Revenue forecast | Q14 Promotion effect | Q21 Suppliers who kept orders waiting |
| Q7 Volume shipping | Q15 Top supplier | Q22 Global sales opportunity |
| Q8 Market share | | |

With `--once` each client runs the 22 queries once in its own random order,
which is TPC-H's stream model: one client is a power test, several clients
are a throughput test. Without it the run is a continuous random stream
with equal weights, for as long as `-T` says.

The queries live in `scripts/pgmh_queries.lua` as a dispatch table; each
transaction's script is one call into it, so changing a query or its
parameter ranges is a Lua edit.

## Reading a run

The spec reports a stream: the elapsed time, the geometric mean of the
query times and where the time went, query by query, in the console and the
HTML report, which adds a timeline per client. The elapsed time of a
`--once` run is the stream's result. The queries per hour headline is
a plain rate over the queries executed; it is not the TPC-H QphH composite,
which only an audited run may report.

## Deviations from TPC-H

- Each client's query order is a random permutation rather than the fixed
  permutations the specification assigns to its streams.
- No refresh functions: the data is read-only during a run.
- The data is generated by the spec's Lua loader with the TPC-H
  cardinalities and value ranges, not by the official generator; text
  columns are synthetic.
- Secondary indexes the specification leaves to the implementer, as listed
  above.
