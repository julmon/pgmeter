# PGM-DS

A decision-support workload derived from TPC-DS: the full 24-table snowflake
schema of a retailer selling through stores, catalogs and the web, its
foreign-key graph, and a representative set of 12 analytical queries. Like
PGM-H it is meant for a single client and read by the per-query response
times; the headline figure is queries per hour.

```bash
pgmeter spec new pgm-ds -o .
pgmeter -d benchmark init --spec pgm-ds -s 1 -j 4
pgmeter -d benchmark run  --spec pgm-ds -c 1 -T 900
```

## Scale and data

The scale unit is a **scale factor**. The dimensions that do not scale are
loaded once; the rest grows with the scale factor.

Fixed dimensions: `date_dim` (every day from 1900 to 2100, about 73,000 rows), `time_dim`
(86,400 seconds of a day), `customer_demographics` (1,920,800),
`household_demographics` (7,200), `catalog_page` (11,718), `promotion` (300),
`reason` (35), `income_band` (20), `ship_mode` (20), `store` (12),
`call_center` (6), `web_site` (30), `web_page` (60), `warehouse` (5).

| Table | Rows per unit | Notes |
|---|---|---|
| `customer` | 100,000 | |
| `customer_address` | 50,000 | |
| `item` | 18,000 | |
| `store_sales` | 2,880,000 | sales dated 1998 to 2002 |
| `catalog_sales` | 1,440,000 | |
| `web_sales` | 720,000 | |
| `store_returns`, `catalog_returns`, `web_returns` | 10%, 14% and 14% of the matching sales | each return points at a real sale line |
| `inventory` | about 11,700,000 | item by warehouse by weekly snapshot |

Scale factor 1 is a few gigabytes and takes a while to load; start there.
At scale factor 1 there is a single unit, so the fact tables load on one
connection; `-j` still parallelizes the keys, the indexes and the vacuum.
Primary keys on every table, the 73 foreign keys of the snowflake (skipped
with `--no-fkey`), and secondary indexes chosen for the 12 queries' access
paths rather than one per foreign key.

## The queries

Twelve queries shaped after TPC-DS query templates, simplified to this
schema and its date ranges. They cover every sales channel, the returns and
the inventory, which is where a storage engine or an access method gets
exercised:

| Query | Weight | Shape |
|---|---|---|
| Q1 Store sales by brand for a manufacturer and month | 10 | TPC-DS Q3 |
| Q2 Store sales by category for a manager, month and year | 10 | Q42 |
| Q3 Store sales by brand for a manager, month and year | 8 | Q52 |
| Q4 Brand revenue to out-of-town customers | 6 | Q19 |
| Q5 States buying above-average-priced items | 6 | Q6 |
| Q6 Average sale metrics by item for a demographic and promotion | 6 | Q7 |
| Q7 Catalog sales by call center and month | 8 | |
| Q8 Web sales and profit by item category | 8 | |
| Q9 Inventory quantity on hand by warehouse and category | 6 | |
| Q10 Customers ranked by store-return amount | 8 | |
| Q11 Store sales for a single category | 8 | |
| Q12 Total extended sales price per channel | 4 | cross-channel |

The queries live in `scripts/pgmds_queries.lua` as a dispatch table, one
call per transaction, with their parameters drawn at random within the
loaded ranges.

## Deviations from TPC-DS

- Twelve representative queries instead of the 99, with simplified text; a
  weighted random stream instead of the specification's power, throughput
  and maintenance runs.
- No data maintenance: the data is read-only during a run.
- The data is generated by the spec's Lua loaders with TPC-DS-like
  cardinalities and value ranges, not by the official generator.
- The headline figure is a plain rate over the mix, not the QphDS composite.
